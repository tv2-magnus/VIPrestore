This documentation describes the VideoIPath API. The documentation is divided into different modules as shown below.
This API guide only covers a subset of the VideoIPath API that has been released for external use. Please contact Nevion Support if specific data or operations not included in the current API is required for intergration with external systems.



1 Introduction
The VideoIPath API consists of a REST-based API and a RPC based API. The REST API is data-driven and allows the user to navigate all data models exported by the VideoIPath system using GET requests. Support for POST, PUT, PATCH and DELETE verbs are planned to be released.
The RPC API is function-oriented and allows the user to retrieve and update data in JSON format. Currently, it is necessary to use a combination of the REST and RPC APIs to integrate with the system.

Note that all examples in this API documentation assume that server that we are integrating with.

1.1 Header fields
Every REST response includes a header and _meta structure as shown below. The header structure was introduced in version 6.8 and onwards, while the _meta structure has been included since version 5.0. Note that no specific order of the data, header or _meta fields should be assumed.




The _meta field is deprecated from release 6.8 and new implementations should use the header field, but it is still included for backwards compatibility with existing integrations.
Description of header fields:
• auth: boolean indicating if the user is authenticated (if not authenticated no data is returned)
• code: this is set to 0 if successful, otherwise an internal error code is set
• errorDetails: includes relevant detailed text descriptions of the error (note this is an array structure)
• infoDetails: includes relevant detailed text descriptions pertaining to the request (normally this is empty and note this is an array structure)
• details: summary of errorDetails or infoDetails field
• msg: human readable message representing the code field above
• user: the authenticated user that issued the request (or "anonymous" if not authenticated)
Note that in subsequent examples the headers are not included as they are common for all REST requests.



1.2 Subscriptions
Information under the /data node in the REST API may contains huge volumes of data. To listen to data changes from the server under the /data node, the REST API supports data subscriptions to efficiently export data changes from the server.
Subscriptions are accessed using the private REST session object. When logging in to a VideoIPath server, a session object is created on the server. This object maintains and manages all subscriptions that are used for a given session.


The subscriptions for a current session is accessed under the following URL:
http://<VideoIPathAddress>/rest/v1/sessions/me/subsc

1.2.1 Adding a new subscription
Adding a new subscription is done by issuing a POST request towards the /rest/v1/sessions/me/subsc no de. The subscription "path" information is embedded in a JSON document in the body of the request. Note that the format of the "path" attribute in the format document follows the URL format used by GET requests.
Example: To create a subscription equivalent to the normal GET request:
GET /rest/v1/data/status/alarms/current/**
Use the following subscription POST request: POST /rest/v1/sessions/me/subsc Content-Type: application/json
{ "path": "/status/alarms/current/**" }
This gives the following example response, which contains all current alarms in the system:



In response to a subscription posting, the entire data set matching the query is returned. The format of the
response corresponds to the format returned by a normal GET request.
Note that in the returned response, there is an _id attribute. This value is allocated by the server and should be used in subsequent requests for this subscription.

1.2.2 Fetching a subscription change event
At any time, the client may ask the server for potential subscription changes. To fetch and acknowledge a change, issue a POST request towards the /ack node as shown below. Note the subscription ID as returned in the initial response. If data is changed since the last request, the data node is populated as shown in the example below.
POST /rest/v1/sessions/me/subsc/1/ack Content-type: application/json
Body: <empty>

In case there are no changes since last poll, the data node is set to null.
Subscription change events closely follows the data format as reported directly from the /data node.
The most important attribute is the "	" (event) attribute, which indicates the type of event that applies to the
object that it is contained in. This may be set to one of the following values:


_e attribute valueDescriptioneEmpty. Normally not used, but in case it is set, the entire content from this object and below can be safely ignored.uUpdate. The children of this node has been updated. Only updated IDs are present in the object. All existing children that aren't contained in this object should be kept unchanged.dThis object has been deleted and should be removed from it's parent.rFull refresh. Between two consecutive ack operations, several events may occur internally to update the subscription. In this time window, change events are merged internally. If an item is added and deleted within this window, a "deleted" event will be reported. External code should handle this case and simply ignore these deleted events.

1.3.1 Priority
The RPC API allows requests to be issued with different levels of priority. This is specified using the priority field in the RPC API header below. The default priority is "normal".



The following priority values are supported:
• "low" : background requests that does not need any priority
• "relaxed" : background requests that are not time critical but prioritized above "low"
• "normal" : this is the default priority used if none is specified (also includes UI requests)
• "high" : foreground requests
Note that priority may be specified for all RPC calls, but will only have significant impact for certain calls including connections requests that may be queued by the system.



1.3.2 Subscriptions
Some API requests supports subscriptions, which means that it is possible to specify a subscriptionId. This means that all data is retrieved only on the first request, while subsequent requests with the same subscriptionId retrieves only updated data since the last request. This is used to limit the amount of data that is retrieved with every poll for new data from the server.

1.4 Authentication
The VideoIPath REST and RPC APIs are based on HTTP, but can also be invoked over HTTPS using SSL/TLS, in order to encrypt the communication between client and server.
User authentication is performed either using basic authentication or using cookie-based authentication.
Basic authentication is normally used for machine-to-machine integration and involves setting the "Basic- authentication" HTTP header to a Base64 encoded string with "user:password".
Base64 does not provide any significant protection against evesdropping, so for external communication the solution is dependent on HTTPS to ensure privacy and prevent interception of passwords.

1.5 General

1.5.1 Time
The API uses UNIX timestamps for all time values, which means number of milliseconds since January 1st 1970 in UTC. Note that the legacy APIs uses number of seconds and not milliseconds. All timestamps are given and reported in UTC and any conversion to local time zone and daylight savings time is the responsibility of the client.

1.5.2 Compression
The requests specified here return large amounts of JSON formatted data. For this reason it is necessary (or at least highly recommended) for performance reasons to use compression.
The API client should indicate that it supports compression using the following header:
Accept-Encoding: gzip, deflate
The VideoIPath server will indicate that data is compressed using the following header:
Content-Encoding: gzip

3 Modern Services
The Modern Services API replaces the Legacy Services API and offers advanced functionality for creating, retrieving and modifying services within the system.
The Modern Services API is designed to handle many different kinds of services. It does so by separating what is service type specific from what is general for all service types. For example, schedule information is the same regardless of whether you are booking a connection or maintenance, however, a profile id only makes sense in the context of a connection.

3.1 Terminology
• Allocated booking: A booking becomes allocated once it has passed validation and has computed a result,
e.g. a path for a connection.
• Booking: The complete representation of a specific service with schedule information as well as service type specific information.
• Booking ID: A unique id given to the booking at create time and will never change.
• Booking instance/instanced booking: A booking scheduled once from a specific start time to a specific end time.
• Endpoint: A topology vertex that is marked with use as endpoint.
• Locked: A user has locked the service. Only this user or an admin user can unlock it. Unless the service is unlocked, modifications will be prevented.
• Revision: Every time a specific booking is changed it gets a new revision represented as a string member 'rev'.
• Recurrent booking: A recurrent booking is a recurrent generator of normal "one time, start-end" bookings. Instead of having a specific start and end time, we specify a pattern which describes at which recurring times a normal booking should be generated. E.g. daily from 12-16 from next Friday until two weeks. At 11 Friday there will be only one recurrent booking registered, but at 12-16 Friday there will be both the recurrent and the active instance registered, unless this is the last instance of the recurrent booking.
• Recurrent instance: An instanced booking automatically created by a recurrent booking. No notable differences from a standard instanced bookings except the id and service id will be suffixed with #n, where n is the number of bookings generated by the recurrent booking so far.

3.2 APIs
All service types are set via the same POST /api/... routes:
• /api/setModernServices
• /api/updateModernServices
• /api/cancelModernServices
• /api/modernServicesAsync
For short we will refer to these APIs as "get", "set", "update", "cancel", and "async", respectively.
It is intended that a client either uses set+update+cancel or async+update (async also supports cancelling). In practice consumers of the async API rarely needs to use the update API, as more often than not, editing a service in the context of the client results in a new connection in VIP.
The Modern Services API may be used in combination with the following GET /rest API. The get API should be used to read/update state independent of which API is used to change the state. Parsing results of booking updates should primarily be necessary in the event of failures, after which you would get no state update from the get API.
• /rest/v1/data/status/pathman/currentModernServices

Validation
There are four layers of validation.

Incoming request validation:
First barrier validation like authentication, raw json validation against the backend data models. If the request is unauthorized or required fields are missing etc. the request will fail with an HTTP error.

Entries validation:
At this stage the json data has been successfully deserialized, and we can validate the contents of the data in the context of the backend state.
Failures at this stage is typically requesting to update a booking with an id that is not present, or updating a connection service with something else than a connection update definition.

Booking validation:
At this stage a number of standard checks are performed. A request will fail if...
• An instanced finite booking duration is more than a year
• Start is before end
• A recurrence pattern with zero active instances is requested
• The revision provided in update/cancel is wrong
• A child of partial services is attempted to be updated/cancelled by a user
• A locked booking is attempted to be updated/cancelled
• A locked booking is attempted to be unlocked by a user with no such permissions


• ... service type specific validations (see respective service type section)

Result calculation:
A result is attempted to be calculated, e.g. a path for a connection booking. If path finding succeeds we are able to allocate the booking and succeed the request entry. If no such path is available, a result is generated with detailed information about the failure.

3.5 Asynchronous Modern Services

The asynchronous modern services API is commonly referred to as the async API. It is possible to combine the async API with the update API (/api/updateModernServices), but in practice this is rarely necessary as a change is usually implemented by creating a new connection using the async API. The async API also supports cancelling connections directly without using another API.
The purpose of the async API is to facilitate streaming of connection requests from an external system to achieve higher throughput. The async API also allows the VideoIPath system to optimize the routing and configuration pipelines as requests are not synchronously processed by the system.
The async API does not support scheduling. All connections created using the API will be scheduled from now until infinity.

3.5.2 Request Status
This section describes how to retrieve status concerning pending requests made over the async API.
Request example:

Response example:

The header object is a generic object in all VideoIPath responses and can be ignored. All the relevant information is provided in the data object.


All responses to pending async requests will be posted on /rest/v1/data/status/conman/asyncResponses as a map from booking ID (obtained from the async response with pending=true) to a status code.
A response will be available for 10 seconds. The response will be logged in the system log, so the information is not lost forever, just not available directly to the client to avoid overload in the event a lot of services are repeatedly requested.
Typically you want to observe changes to the async responses to ensure that requests are fulfilled without errors. Alternatively you can use the async api as a more fire and forget style. Typically these are the cases you end up in:
1. Response code 8 (already ok): This results from pending=false with zero errors and can be handled in the client response directly.
2. Other positive codes: This results from pending=true with zero errors, and ends in a REST update and could be handled directly from there.
3. Negative codes (errors): This results from a booking error (e.g. no path). This will not result in a REST update
and should be handled by the client. A negative code means that the connection is not created.
This leads to two primary paths to select:
1. Handle all responses from the async responses API as well as booking updates from the REST API.
2. Handle timeouts in the client and pending=true requests that doesn't respond in a given time mark as suspicious and potentially an error.
For a complete list of status codes please refer to the general modern services page. However, in most cases it is sufficient to treat positive codes as success and negative codes as error.

Federation is a way to connect multiple systems together and to be able to establish connections between the systems. Each system is responsible for its local resources and can operate completely autonomously in case communication between the systems is broken.
There are two different federation models:
• Public endpoints. In this case endpoints from a system may be marked as public and exposed to another system permanently as external endpoints.
• Handoff point. In this case any local source may be routed to a handoff point between two systems. The source will temporarily be exposed to the other system for the duration of the connection in the originating system.
